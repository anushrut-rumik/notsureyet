```text
## Four principles

**Queryable**

Filter and paginate records through indexed attributes with a Web2-like query language. No external indexer.

**Time-scoped**

Every entity has an expiration block. When it arrives, the entity leaves the query surface. You pay for the lifetime you choose.

**Tamper-proof**

Every write is a signed Ethereum transaction. State is committed with a keccak Merkle-Patricia trie, so any change is evident.

**Wallet-owned**

Only the owner wallet can update, extend, transfer, or delete an entity.
```

```text
**We already use all four principles, but we do not yet turn all four into strong user-facing features.** The foundation is substantial: Arkiv holds the task state that the agent reads to list and recover work. The biggest opportunity is to make **payment requests, approvals, and receipts independently queryable and useful across wallets and applications.**

For this product, transactions are a strong focus. Arkiv’s role would be to hold the agreement and progress around a transaction. The payment itself still settles on the payment network.

I checked the current source, the installed Arkiv SDK **1.0.1**, and Arkiv’s published guidance. This is an implementation assessment; I did not perform a new live payment test.

**Where we stand today**

| Principle | What we currently do | What is still missing |
|---|---|---|
| **Queryable** | Index task identifiers, revisions, operation identifiers, and chat scope. Task listings query Arkiv directly, with pagination and wallet filters. | Payment-specific questions still require downloading and decrypting task snapshots. We cannot directly filter payments by network, status, or deadline. |
| **Time-scoped** | Each checkpoint has a roughly 30-day lifetime. Unfinished tasks publish a fresh checkpoint weekly while the application runs. | Expiration mostly manages storage retention. It does not yet create a visible product experience around expiring requests, offers, or quotes. |
| **Tamper-proof** | Publish signed, read-only checkpoints. Verify successful transaction receipts and read back the stored checkpoint. | We lack a clear, independently verifiable timeline connecting the payment request, exact approval, submission, and settlement evidence. |
| **Wallet-owned** | The selected storage wallet creates and owns its checkpoints. Connected MetaMask wallets approve storage writes themselves. | Ownership does not yet give users easy portability between clients. Encrypted contents still depend on the local encryption key, and existing readers reject ownership changes. |

These behaviors are visible in the [Arkiv bridge](<project>/integrations/arkiv.mjs:11), [checkpoint recovery](<project>/agent/arkiv.py:313), and [retention maintenance](<project>/agent/arkiv.py:608).

Two distinctions matter:

- **Read-only does not mean permanently available.** It prevents changes to the entity’s attributes. The owner can still delete it, and expiration removes it from live queries. [Arkiv creation documentation](https://docs.arkiv.network/writing/create/)
- **Wallet ownership and self-custody are separate.** Our agent-created wallet has its signing key in the application’s encrypted local vault. The MetaMask path gives the user direct control of signatures.

**What “full use” should mean for us**

The organizers’ published criteria ask whether the fields we filter, ownership rules, and expiration choices fit the product—and whether those features change something users see. They explicitly exclude a log that nothing reads. They do not require using every available SDK operation. [Arkiv judging criteria](https://ethglobal.com/events/mumbai/prizes/arkiv)

Our existing task recovery is useful. However, deliberately making the application depend on Arkiv is weaker evidence than showing a capability users gain from it.

**My recommendation: build a wallet-owned payment workspace.**

The core experience would be:

> “A payment request can be discovered, reviewed, approved, tracked, and independently checked through wallet-owned records—even if the original chat or application is unavailable.”

Here is how I would develop that.

**1. Give payment requests their own queryable records**

Currently, a payment is embedded inside an encrypted task snapshot. Create a dedicated payment-request entity with a stable identifier.

With the user’s chosen disclosure settings, index fields such as:

- Request type and intended payer or recipient.
- Source network and destination network.
- Asset.
- Request deadline.
- A reference linking subsequent approval and settlement records.

Keep private instructions, personal details, and sensitive amounts encrypted where appropriate. Every indexed field is publicly visible; encryption does not make those fields private.

This enables useful queries such as “requests addressed to my wallet that expire today.” It also allows another compatible client to find the same records without our API.

For payment status, define which records count as the latest authoritative state. Simply finding an old “pending” record must not make a completed payment appear actionable.

**2. Make expiration correspond to real user decisions**

Different records deserve different lifetimes:

| Record | Purpose of its lifetime |
|---|---|
| Payment request | Stop presenting an unpaid request after its deadline. |
| Fee quote | Require a fresh review when network costs change. |
| Agent task checkpoint | Keep unfinished work recoverable. |
| Settlement receipt | Preserve evidence for the user’s chosen retention period, with renewal or export. |

Today, we use one general checkpoint lifetime. These separate lifetimes would make Arkiv’s time-scoped design visible in the product.

**Storage expiration must remain separate from payment authorization.** Before signing, the executor must check the request deadline and exact approval again. A cached request or an extended storage lifetime must not extend permission to pay. Arkiv’s expiration operates in blocks, so calendar-time estimates are approximate. [Arkiv expiration documentation](https://docs.arkiv.network/writing/expiration/)

**3. Create a verifiable transaction history**

Connect separate records for:

1. What was requested.
2. What the user approved.
3. Which transaction was submitted.
4. What settlement was independently observed.

The approval should bind the exact recipient, amount, asset, network, and relevant limits. For independently verifiable user authorization, add a wallet-signed approval message; an application-written checkpoint alone proves the application published something.

For cross-chain payments, link the source transaction, cross-chain message identifier, and destination transaction. Show the destination outcome separately from source submission.

This builds on our existing protection: the code already persists payment hashes before network submission and waits for the storage checkpoint. [Payment approval and submission](<project>/agent/wallet.py:372)

A signed record proves who published a claim. The payment networks must still supply evidence that money moved.

**4. Turn wallet ownership into portability**

A compelling demonstration would let a second client:

- Discover the user’s payment records directly through Arkiv.
- Decrypt records the user explicitly grants it access to.
- Check submitted transactions.
- Continue tracking an unfinished payment without sending it again.

This requires portable encryption-key recovery or sharing, a documented record format, and clear execution authority. Connecting the same wallet alone is insufficient.

I would keep tracking portable first. Allowing multiple clients to execute payments introduces coordination risks and needs an explicit rule for which executor may act.

**The most creative extension: requests and receipts shared between two parties**

For example, a freelancer publishes a wallet-signed payment request. The payer’s agent discovers it, prepares the payment, and obtains exact approval. After settlement, the freelancer can publish a separate acknowledgment linked to that request.

Each party owns their own statement. Neither can rewrite the other’s statement. A third client can query the linked records and check the payment evidence.

That gives all four principles a practical role: discovery through queries, deadlines through expiration, attributable statements through signatures, and control through ownership. A recipient acknowledgment would remain optional evidence; its absence would not prove nonpayment.

**What I would prioritize**

Build **one expiring payment-request flow with linked settlement evidence and an independent reader**. Demonstrate it by restarting the agent after submission and recovering the same transaction without another send.

That would deepen the existing implementation considerably. It would also give us a concrete answer to “Why Arkiv?”: users and counterparties could discover and verify shared payment state through their wallets, beyond the original application.
```
