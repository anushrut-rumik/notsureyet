short description:

A WhatsApp agent that manages tokens across chains and remembers unfinished work.

description:

our project lets people manage tokens across blockchains through a WhatsApp conversation. you can ask it to check balances, send tokens, or manage a lending position for a set period. it shows you the plan and asks for approval before starting.

for example, you can say, “manage my test tokens for 30 days.” the agent prepares a plan covering how much it can use, how much must stay untouched, which pools it can use, and how much it can spend on fees. once approved, it checks the pools on a schedule. it compares the expected extra earnings against the cost of moving and the time left in your plan. a higher interest rate alone is not enough to trigger a transfer.

you can ask what happened, compare the pools, pause management, or request a withdrawal in the same chat. the agent tracks a transfer through to its destination and checks that the tokens reached the intended pool before reporting completion.

the other important part is remembering unfinished work. encrypted task checkpoints are stored on Arkiv, so a restarted agent can recover saved progress. transaction records help it investigate an interrupted transfer without blindly sending it again.

the current prototype runs on Ethereum Sepolia and Base Sepolia. we have completed a real testnet cross-chain transfer and destination deposit. the lending pools use simulated interest rates and do not earn real interest.

how it’s made:

we extended an existing Python agent with wallet tools, lending management, and blockchain-backed task storage. WhatsApp messages reach the agent through a separate messaging service and Redis. an OpenAI model interprets requests and calls tools with validated inputs. a background worker handles scheduled checks and follows transactions while the user is away.

the lending calculations live in a shared TypeScript module. it checks balances, pool rates, fees, the remaining management period, and the user’s approved limits. amounts use integer arithmetic to avoid floating-point rounding errors. the application and Chainlink Runtime Environment (CRE) workflow use the same rules, so they do not maintain separate versions of the decision logic. the model handles the conversation, while code calculates whether a move qualifies.

CRE reads contract state and validates the proposed operation. our prototype runs CRE locally, then relays the validated instruction through an application signer. it is not yet a workflow deployed to Chainlink’s decentralized network. Chainlink’s Cross-Chain Interoperability Protocol (CCIP) carries the tokens and instructions between the two testnets. Solidity strategy contracts enforce limits, protect the reserved balance, reject repeated operations, and handle the destination deposit.

we support both an encrypted agent wallet and a connected MetaMask wallet. approval is tied to the actual incoming user message and the specific review shown in that chat. the model cannot approve its own proposal.

Arkiv stores encrypted task checkpoints and a separate encrypted lending activity history. this gives users a record outside our application database. private contents require the encryption key to read. SQLite holds local execution records, chat history, and transaction journals.

one tricky bug was that a transaction could report success even when an inner contract call failed. we added checks for the expected contract events and token movements before marking an operation complete. we also save the signed transaction and its hash before broadcasting. if a response disappears, recovery checks that original transaction instead of creating another transfer.

we used Foundry for contract tests, pytest for the Python agent, and Node and Bun tests for the TypeScript rules and CRE integration. recovery tests cover interrupted processes, missing responses, repeated approvals, and pending transfers.
